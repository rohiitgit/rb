## New findings

### M1: major. A method only Tree-sitter sees is "paired" with a javac local or field of the same name. Its calls and overrides become exact edges from a method that does not exist.

**Cause.**

`definitions_unpaired` (`crates/rb-indexer/src/scip.rs:768`), rule (b) at `:790`, accepts a Tree-sitter definition as paired when `anchors.occurrences` holds any anchor for it. `Anchors::new` (`:626`–`:642`) produces anchors of three kinds:
- a **local** definition occurrence at the name whose display name equals the definition's name. The local can be any local: a local variable, a lambda parameter, an anonymous class's method;
- any **global** definition occurrence at the name that `may_name` accepts. That includes a field (`C#n.`).

Amendment 54 meant the local binding for scip-java's enum-constant bodies, but nothing restricts it to them.

Once anchored, `structure_disagreement`'s clauses 1 and 2 (`:672`, ranges at `:688`) check the reference against **the anchor's own range**. That is the local's or the field's range, which contains the call by construction, so both clauses pass.

The only signal is `definitions_local` (a local anchor) or nothing at all (a field anchor).

**Repro.** Real image, `--no-cache --force`, project `t10esc` (UTF-8 pom, ASCII sources). javac compiled every file, and `rb status` reads `documents rejected 10 (structure_disagreement 10)`: the eight Hid files, Bal1 and AnnQ. `unmatched 0`, `definitions without occurrence 0`, `3 local definitions`.

### M2: minor/doc. TypeScript merge-conflict markers restructure a file for the TypeScript compiler only, and a method only Tree-sitter sees sources an exact edge.

**Cause.**
- The TypeScript scanner treats a `=======` line as trivia up to the next `>>>>>>> ` line, and `<<<<<<< ` / `>>>>>>> ` lines as trivia to the end of the line (`isConflictMarkerTrivia`).
- Tree-sitter-typescript 0.23.2 parses those lines as `ERROR` and keeps everything between them.
- No structure, pairing or syntax-error check runs for TypeScript (`scip.rs:226`). `definition_disagreement` sees nothing, because the TypeScript compiler has *fewer* definitions.

**Repro.** Real image, `t10ts` (npm, lockfile, `tsconfig.json`). `src/conflict.ts`:

```
export function helper(): number { return 1; }
export class C {
  m1(): void {
=======
  }
  m9(): void {
>>>>>>> x
    helper();
  }
}
```

- scip-typescript gives `C#m1().` enclosing `[2,2,8,3]`, holding the `helper` reference at `[7,4]`. It has no `m9`.
- Tree-sitter sees `m1` `[2,2,4,3]` and `m9` `[5,2,8,3]`, with a syntax error at `[3,0]`.
- Exact edge: `` rb-heuristic … `src/conflict.ts`/C#m9(). CALLS src/`conflict.ts`/helper(). `` at `[7,4]`. False: `m9` does not exist for the compiler, and the true `C#m1() → helper()` is lost.
- Status line: `documents rejected 0`, `unmatched 0`, `definitions without occurrence 1`. A `syntax_error` diagnostic is emitted, but the file stays SCIP-owned.

**Status.** Amendment 71 lists "TypeScript is not checked for structure … a TypeScript-only restructuring not yet found would rely on `definition_disagreement` and the name guard" as uncovered. This is such a restructuring, so the finding is minor/doc. The amendment's sentence "the remaining differences known … are converted" should now name conflict markers.

**Cheap closer.** Apply rule (s) to TypeScript: a Tree-sitter syntax error rejects the document. Measured: 0 `syntax_error` diagnostics on class-validator, so 0 rejections. Rule (b) for TypeScript would need calibration first: class-validator has `definitions without occurrence 1`.

**Regression test.** A join unit with the measured `conflict.ts` occurrences, expecting a rejection.

### M3: minor. Classes that reference themselves in an annotation lose all coverage: the class is anchored to its implicit constructor.

**Cause.** In two vavr test classes scip-java places the type's definition occurrence on the first mention of its name, which is inside the class's own annotation:
- `@ExtendWith(FutureTest.TraceUnitExtension.class)`: `FutureTest#` defined at `[67,12,67,22]`, enclosing `[66,0,1553,1]`;
- `@ExtendWith(JavaConvertersTest.TestTemplateProvider.class)`: `JavaConvertersTest#` defined at `[43,12,43,30]`.

At the real name `[68,13]` there is only the implicit `` FutureTest#`<init>`(). `` occurrence, which has no range.

`Anchors::new` tries `global_at_name` (`scip.rs:626`) before the amendment-7 by-name fallback. `may_name` accepts a constructor at its type's name (`rb-scip/src/symbol.rs:41`), so the class is anchored to `<init>`. The type's own occurrence, which has a range, then pairs with nothing, and rule (a) rejects the document.

**Measured.**

| | vavr @ `7791b586d290` |
|---|---|
| `bf43351` | `documents rejected 2 (structure_disagreement 2)` (`FutureTest.java`, `JavaConvertersTest.java`); 26,000 `CALLS` / 5,982 `IMPLEMENTS` / 86 `REFERENCES` exact; 1,649 heuristic code edges in those two files |
| `5502422`, same cached index | 0 rejected; 27,257 / 5,993 / 91. The two class nodes were keyed `` …FutureTest#`<init>`(). `` and `` …JavaConvertersTest#`<init>`(). `` with kind `class`, and the class's `REFERENCES AbstractValueTest#` carried the constructor's key |

**Assessment.**
- The fix turned a silent mis-key into a counted whole-file loss: 1,273 exact edges, 2 of 258 Java documents (0.8%).
- Not a soundness defect.
- Not documented. The pattern is ordinary code: a class annotation naming a nested type of the class (`@ExtendWith(Self.X.class)`, `@JsonDeserialize(builder = Self.Builder.class)`), together with an implicit constructor.

**Suggested fix.** For a Tree-sitter type definition, accept only a type occurrence (descriptor `#`) at the name, and otherwise fall back to the by-name type occurrence before the name. Equivalently, never anchor a type to a range-less `<init>`.

**Regression test.** The measured `FutureTest` occurrences: the type at the annotation token with its range, and `<init>` at the name with none. Expect the class keyed `FutureTest#` and the document accepted.
