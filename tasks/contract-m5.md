# M5 contract: scale and API — REST API with guard rails, snapshot lifecycle, `rb diff`, AGE loading, fetch-phase egress, benchmark (draft, planner, 2026-10-07)

Written before any code. M5 is done only when every assertion below is backed by a passing test or a recorded measurement. Nothing here is built yet. "Verified facts" are only what was read in the code, the goldens or the records at commit `afae548` (M4b closed, `PIPELINE` `m4b-di-8`).

This contract follows the M4b format and applies, from the start, the lessons M3b, M4a and M4b paid for:
- the soundness claims and the closing bar are stated before any review (lesson 2026-10-06, "state the soundness bar before adversarial review starts, and close on verification");
- allow-lists, never deny-lists, wherever a guarantee is adversarial (the egress proxy, the server's Host check, the read-only role);
- growth is tested by counted operations, never by wall clock (lesson 2026-10-06, "growth tests count operations");
- performance targets are measured with profiles and stated as measured numbers, with hardware and load noted; a missed target is a documented gap, not a failure (design §13's exit criterion).

## Soundness claims and closing bar (read first)

M5 adds no new kind of code edge. It adds surfaces whose failure is silent in a different way: an API answer that differs from the CLI's, an answer cut short without saying so, a snapshot read half-deleted, a retention run that removes what a user still needs, a diff that misses a change, a projection that differs from its source, and a fetch container that reaches a host it should not. For each, the table states the claim, the mechanism, and the residue. **Everything not proven takes the safe direction:** a request that cannot finish within its limits is an error or carries a named `truncated` limit; a snapshot that cannot be read whole is an error; a host not on the allow-list is unreachable.

| Surface | Claim (exactly this, no more) | Mechanism | Residue (out of scope by construction) |
|---|---|---|---|
| REST answers (S12–S14) | For the same snapshot and parameters, the body of every `GET`/`POST /v1/…` response is byte-identical to the stdout of the matching `rb … --json` command, and an error response's body is byte-identical to that command's `--json` error output; the HTTP status maps one-to-one from the CLI's exit code (D5). | One request layer (`rb-api`, D2) builds every result and envelope; CLI and server only serialise it. An e2e test compares bytes per endpoint, fixture and parameter set, ambiguous, not-found and truncated cases included (S14). | Text output (`rb callers` without `--json`) is CLI-only rendering of the same result and is not compared. Transport-level failures (a connection reset, a client timeout) are not API answers. |
| Guard rails (S10) | No answer is partial without saying so: whenever a walk stops early, the result's `truncated` list names every limit that stopped it (`depth`, `hops`, `nodes`, `tree`, `work`, `rows`), and when `truncated` is empty the answer equals the uncapped computation. A request that exceeds its wall-clock deadline or finds the server saturated gets an error (`503`, `deadline_exceeded`/`busy`), never a partial body. | Every cap sits in the walk that it cuts and records its name there; a property test lifts the caps on random graphs and compares (S10); the work cap counts operations (`work::tick`, made real), so truncation is a function of the snapshot and parameters, never of machine speed (D6). | None for the claim. The wall-clock deadline does not stop the computation it abandons (it is bounded by the work cap and still counts against the concurrency cap). |
| Snapshot reads (S1) | A reader sees a whole snapshot or an error, never a mix of two states: `load_graph`, `load_diagnostics`, the status counts, `rb dump` and every question read one snapshot inside one `REPEATABLE READ READ ONLY` transaction. | Today the node, edge and evidence queries of `load_graph` run as three separate statements (verified fact 4); a retention that deletes the snapshot between them gives a graph with nodes and no edges. | None. |
| Retention (S3) | Retention never deletes the live snapshot, keeps the `N` newest retired snapshots of each repository (`N` = `--keep`, default 2), removes every `failed` row, and leaves exactly one AGE graph per repository: the live snapshot's. No `building` row survives its process. | Snapshot rows are written inside the publish transaction (a crash leaves nothing, and a failure records a separate `failed` row after the rollback); retention selects only `retired` and `failed` rows; graph DDL runs under one database-wide advisory lock and drops one graph per transaction (D10). A property test drives random sequences of publish, failure and retention and checks the invariant after each step. | Rows written by binaries before M5 (stale `building` rows) are removed by `rb gc`, which reports them; it never runs implicitly. |
| `rb diff` (S16, S17) | For any two snapshots A and B, the node and edge sections of `rb diff A B` are exactly the difference of their canonical dumps by natural identity: applying the diff to A's node and edge lines yields B's, byte for byte; `diff(A, A)` is empty; `diff(B, A)` is `diff(A, B)` inverted. The summary sections (endpoints, table access, service dependencies) are pure functions of the two graphs computed by the same code as the Service Card and `rb table-deps`. | Pure functions over `rb_model::Graph` keyed by `(kind, key)` for nodes and `(src kind, src key, kind, dst kind, dst key, provenance)` for edges (the dump's own identities, verified fact 10); the apply property is a unit on random graphs and an e2e on every fixture pair. | Moves are not inferred: a symbol whose key changes is a removal plus an addition (D11, fork F4). When the two snapshots were built with different tools, the diff includes tool-induced changes and its header says which `tool_versions` keys differ (D12). |
| AGE projection (S6) | Each live snapshot's AGE graph holds exactly the snapshot's nodes (label, `nid`, `key`, `name`) and exactly its edges as a multiset (label, start `nid`, end `nid`, `provenance`, `certainty`, and `op` where the relational edge has one). | The CSV bulk loader already used (verified fact 6); the e2e parity check compares the whole vertex set and the whole edge multiset on every fixture, and the benchmark repeats it on both large repositories (S24). | AGE-internal ids (`id(n)`) are not part of the claim. |
| Server exposure (S13) | The server answers only on a loopback address, only to requests whose `Host` header names that loopback address and port, sends no CORS headers, runs every database statement in a read-only session, and runs Cypher additionally as the role `rb_reader`, which can read the `rb` schema and the graph schemas and nothing else. | Startup refuses a non-loopback bind address; an allow-list of `Host` values (`127.0.0.1:<port>`, `localhost:<port>`, `[::1]:<port>`) with `421` otherwise (DNS rebinding); `default_transaction_read_only = on` on every pooled connection; `SET LOCAL ROLE rb_reader` around Cypher (D7, D9). Tests per rule. | Any process of any local user can call the server: there is no authentication (D7). A local user with database credentials can bypass the server altogether. |
| Fetch-phase egress (S21, if fork F2 is decided "in") | During the fetch phase a job's container can open connections only to the egress proxy, and the proxy forwards only `CONNECT <host>:443` for hosts on the allow-list (no plain HTTP): the registries of the built-in recipes plus those a user lists in `rb.toml`. The container cannot resolve external names, cannot reach any other address, and the index phase keeps `--network none`. | An `--internal` Docker network with no route out, a pinned proxy container attached to it and to a bridge network, a fixed proxy address so the job needs no DNS, and a probe suite that tries each forbidden path from a real job container (S21). | Exfiltration through allow-listed registries themselves (data encoded in request paths or headers to `registry.npmjs.org`); domain fronting through an allow-listed CDN (the proxy reads the `CONNECT` host, not the TLS SNI or the inner `Host`); malicious packages served by an allow-listed registry; Docker Desktop VM networking defects; timing side channels. |
| Inherited claims | M4a's `CONSUMES` bar (no false `synthetic` from any form a repository-wide name-token scan can see), M4b's RTA proof (opt-in) and orphan eligibility stand, and every form on the bounded review list (S19) is either fixed or recorded as residue with its example. | S19's fixes, each test-first with a biting row; S20's records. | As in contract-m4a amendment 18 (open item 22) and contract-m4b's soundness table. |

**What M5 must not change.** M5 changes no node, edge, attribute, certainty, provenance, symbol key or diagnostic in any dump, except the named items, each of which can only lower a certainty, remove an edge, keep a symbol alive, or rename an attribute value:
- S18 (M4a open item 6): `base: unresolved` on suffix-matched `CONSUMES` edges whose base did not resolve;
- S19's review fixes: more host-by-name stitches capped (discovery words in every file), XML comments read, fewer orphan-eligible symbols (fragments, unresolved supertype heads), `ambiguous` instead of a single wrong `heuristic` `INJECTS` (registrants), unknown instead of a suffix match (contested bases with an external candidate).

This is invariant 1, checked against `afae548` dumps of every fixture and of the four M4b closing repositories, every differing row classified.

**Closing bar.** Decided now:
1. **Evaluator pass 1 is a full review,** adversarial probing of the claims above included. Each finding is fixed test-first as an amendment.
2. **Evaluator pass 2 is verification-only.** It re-runs every pass-1 finding's repro and its controls, the regression suite and the mutations, the invariant-1 comparison, and the benchmark's determinism checks (fresh == cached on both large repositories). It does not re-run the latency measurements, which are recorded numbers, not pass/fail checks.
3. **A pass-2 result blocks closing only if it is one of:**
   - (a) a pass-1 fix that does not hold;
   - (b) a regression;
   - (c) a failure of a claim above through a form its mechanism controls: an API body differing from the CLI's; a partial answer with an empty `truncated`; a mixed-snapshot read; retention removing the live snapshot or one of the `N` newest retired ones, or leaving a second AGE graph; a diff that does not reproduce B from A; a projection differing from the relational rows; the server answering a non-loopback peer or a foreign `Host`, or writing; a fetch container reaching a non-allow-listed address by TCP, UDP or DNS; a false `synthetic` `CONSUMES`, a pruned-but-instantiated type or a false orphan from a form on S19's list;
   - (d) a non-deterministic dump or response body;
   - (e) a failed test, guard or verification step.
4. **Not blocking:** a new attack form in a residue class above (recorded as an M6 open item with its example); a §12.5 target missed with its profile recorded (design §13's exit criterion says "met or gaps documented with profiles"); a precision miss that contradicts no stated rule.
5. **Performance is measured, not asserted.** Every number in S24–S26 is stated with the hardware, the Docker VM's allocation, the host load average at the start and end of the run, and the sample count; a target is "met" only when the p95 of the stated samples is within it.

## Scope

**In (M5):**
- **REST API (design §11.2)** with guard rails, read-only and local-only (D1–D9, S11–S15), served by `rb serve`.
- **One request layer (`rb-api`)** shared by the CLI's `--json` output and the server, so that the two cannot drift (D2); `rb callers --json` (M4b open item 10), `rb status --json`, `rb find --json`, `rb snapshots`.
- **Snapshot lifecycle:** consistent reads (S1), a database-wide lock around AGE graph DDL (S2, design §14), retention (S3), `rb gc` and `rb cache prune` (S4), `--no-cache` that refreshes the facts it bypassed (S5, M4a open item 4).
- **Bulk AGE loading:** the CSV loader exists (verified fact 6); M5 adds the lock, full parity, `op` on `QUERIES`/`MIGRATES` edges (design §8.4 says so; not built, verified fact 6), and a measured profile on the large repositories (S6, S24).
- **Cypher guard rails:** a configurable statement timeout, a row cap, the `rb_reader` role (S7); the e2e suite's robustness against the 2 s timeout and leftover graphs (S8).
- **A prebuilt per-snapshot index** shared by every question, the design's in-memory adjacency (§8.4, "In-memory CSR"), so a warm server answers without rebuilding adjacency per question (S9).
- **`rb diff`** (design §11.1): exact node/edge sections plus endpoint, table-access and service-dependency summaries (S16, S17).
- **Fetch-phase egress allow-list and per-repository SCIP caches** (contract-m3b amendment 81, design §14), fork F2 (S21, S22).
- **The bounded adversarial review** of M4a's carriers and M4b's DI, RTA and orphans (S19, S20).
- **M4a open item 6** (`base` on suffix edges, before the API exposes edge attributes; S18).
- **Benchmark on two large public repositories** against design §12.5 with profiles (S23–S26), which also carries every "measure on the M5 benchmark" item: M4a open items 8, 10, 11, 22 (with amendment 15's follow-up, the cost of amendments 14–17), 23; M4b open items 6, 7, 11, 19 (measured, not changed); M3b's TypeScript interface-method `IMPLEMENTS` count.

**Out of M5, with the reason:**
- **`POST /v1/repos/{repo}/index` (design §11.2) → not built in M5.** Indexing runs repository builds (the fetch phase executes the project's own Maven plugins); a write endpoint on an unauthenticated local server is reachable from any local process and, without the Host check, from a browser. Indexing stays a CLI action. Revisit with authentication (M6).
- **The thin-client CLI mode (`RB_SERVER`, design §11.1) → not built.** The identity test (S14) already proves the two surfaces agree, and a client mode would add an HTTP client dependency for no answer the embedded mode lacks. Design §11.1 is annotated.
- **Authentication and remote binding → M6** (D7).
- **Move detection in `rb diff` (design §5.1) → not in M5** (fork F4): it needs a definition-body hash that no fact holds today; adding one changes every symbol's attributes in every dump.
- **Partition-per-snapshot storage (design §8.3, "v2") → not planned.** Retention deletes rows by snapshot id; its cost is measured on the benchmark (S24) and recorded.
- **Edge-delta loading (design §3.4, v2) → not planned.** The incremental target (S24) is measured with whole-snapshot assembly.
- **Precision items assigned to M5 by earlier contracts → M6** (fork F5), each measured on the benchmark where it applies:
  - M4b 5 (gate M reads test sources), 6 (RTA yield), 7 (Spring Boot module role), 19 (module-object approximation): each changes which edges or attributes are produced and needs its own soundness argument; RTA is opt-in and `INJECTS` is capped at `heuristic`, so no default answer is wrong because of them.
  - M4a 16 (constructor-assigned members), 19 (user information with a hole), 20 (configs passed by name): new folding rules with their own adversarial surface; none occurs on the measured repositories (grep counts recorded in S26).
- **SCIP build breadth (contract-m3b amendment 81: effective source encoding, TypeScript restructurings, Gradle, M6 build recipes, workspace installs, tsconfig include/exclude) → M6,** as already assigned.
- **Facts-cache compaction or compression → M6,** unless the benchmark measures the cache above its disk budget (D13), in which case it is a documented gap with the measurement.

## Engineer declaration

**Canonical state:**
- **Migration `0006_reader_role.sql`** (new): the role `rb_reader` (`NOLOGIN`), `USAGE` on schemas `rb` and `ag_catalog`, `SELECT` on `rb.*` and on `ag_catalog.ag_graph`/`ag_label`; the publish transaction grants `USAGE` on the new graph's schema and `SELECT` on its tables to `rb_reader` (S7). It changes no table.
- **Snapshot rows:** unchanged columns. Their lifecycle changes: a row is inserted inside the publish transaction, `age_graph` is set to `NULL` when its graph is dropped at retirement (D10).
- **No graph change** beyond the named items (S18, S19). `rb_indexer::PIPELINE` becomes `m5-1` at the first of them and is bumped on each later one. `rb_scip::RECIPE` is bumped by S21/S22.
- **Configuration:** `rb.toml` gains `[scip] registries = [...]` (extra allow-listed hosts, S21). Nothing else.

**Derived** (never stored):
- the per-snapshot index (S9), held by the server per live snapshot and built once per CLI invocation;
- every API envelope and result (S11);
- `rb diff`'s sections and summaries (S16, S17);
- the benchmark's measurements (recorded in this contract, not in the database).

**Invariants:**
1. **Dumps unchanged** except the named items (soundness section). Checked against `afae548` dumps of the three fixtures and of spring-petclinic, spring-petclinic-microservices, realworld-spring and jhipster-sample-app at M4b's pins, with every differing row classified by item.
2. **API ≡ CLI.** One `rb-api` call produces both bodies; byte equality is tested per endpoint (S14). The CLI's text output is a rendering of the same result struct.
3. **No silent truncation.** Every cap names itself in `truncated`; `truncated` empty implies the uncapped answer (S10).
4. **Whole-snapshot reads.** Every read of a snapshot is one `REPEATABLE READ READ ONLY` transaction (S1).
5. **Retention.** The live snapshot is never selected for deletion; exactly one AGE graph per repository with a live snapshot exists after any publish or retention completes; graph DDL (`create_graph`, `drop_graph`) runs only under `RB_AGE_DDL_LOCK` and one graph per transaction (S2, S3).
6. **Projection parity.** Vertex set and edge multiset equal the relational rows (S6).
7. **Read-only, local-only server** (S13): no statement the server issues can write (read-only sessions; a unit lists every SQL text `rb-api` issues and checks it is a `SELECT` or a read-only `cypher()` call).
8. **Determinism.** The same snapshot and parameters give byte-identical response bodies (no time, no host path, no request id in a body; timings only in a `Server-Timing` header). Dumps stay byte-identical across fresh/warm caches, two repository names and forced rebuilds.
9. **Bounded work.** Every walk has a visited set and stated caps; every server request has a work cap, a deadline and a concurrency slot (S10, S13). New recursions (diff, pagination, retention sequences) have cycle or termination tests where they recurse.
10. **Stated complexity is tested by counted operations** (≤ 5× the operations for 4× the input): `rb diff`, pagination, the index build, and a depth-1 caller question on the index, which must not grow with the graph at all for a fixed neighbourhood (S9, S16).
11. **Egress** (if F2 is in): the fetch container's network is `--internal`, its only peer is the proxy, and the proxy's allow-list is the recipe's plus `rb.toml`'s (S21).

## Decisions (made here, with reasons)

- **D1: HTTP stack: `axum` on `tokio`, HTTP/1.1 only, minimal features (fork F1).**
  - **Why axum:** design §3 names it; it is the mainstream Rust HTTP server; `tokio` is already in the dependency tree through `postgres` (verified fact 12), so the new crates are `axum`, `hyper`, `hyper-util`, `http`, `http-body`, `tower`, `tower-service`, `tower-layer`, `matchit` and a few small ones; it handles HTTP/1.1 framing, keep-alive and malformed requests in a widely reviewed codebase, which a hand-written server would not.
  - **Features:** `axum` with `default-features = false, features = ["http1", "tokio", "query", "json"]`; `tokio` with `rt-multi-thread`, `net`, `signal`, `time`. Phase 0 builds a scratch crate and records the exact number of new crates in `Cargo.lock`, their licences, and the release binary's size delta; if more than 30 new crates or more than 3 MiB, the orchestrator is asked before phase 9.
  - **Blocking work:** the `postgres` client is synchronous and must not run on a runtime thread; every handler runs its work in `tokio::task::spawn_blocking` under a semaphore (D8).
  - The alternative (`tiny_http`, synchronous, four small dependencies) is recorded in F1.
- **D2: two new crates, one binary.**
  - `rb-api` (no HTTP): request types, parameter validation with the CLI's bounds, target resolution (`pick_target`, `pick_endpoint`, moved from `rb-cli`, verified fact 9), the JSON renderers (moved from `rb-cli`), the envelope, error kinds. Both the CLI's `--json` and the server call it.
  - `rb-server`: the axum binding, the pool, the snapshot cache, the limits. `rb serve` (a subcommand of the one `rb` binary) starts it; there is no separate `rb-server` binary (design §3's box becomes a subcommand; annotated).
- **D3: the server holds one prebuilt index per repository's live snapshot** (S9), plus at most one more snapshot requested with `?snapshot=` (LRU of one). On each request it reads `rb.repo.live_snapshot_id` (one indexed `SELECT`) and, if the pointer moved, builds the new index before answering; requests already running keep their `Arc` of the old one. The index's memory is measured on the benchmark (S24).
- **D4: the envelope.** Every `--json` output and every API body is:
  `{"api": 1, "repo", "snapshot": {"id", "commit_sha"}, "query": {normalised parameters, defaults filled in}, "limits": {the caps in force}, "truncated": [limit names, sorted], "certainty": {histogram over the result's rows, when they carry certainty}, "result": {…}}`.
  `snapshot.id` is in the body (design §9: "every response includes `snapshot_id`"); a test that compares CLI and API bodies uses the same snapshot. Errors are `{"api": 1, "error": {"kind", "message", "candidates"?}}`. Existing `--json` outputs (`rb impact --json`, `rb path --format json`, `rb table-deps --json`, `rb service --json`) become the `result` of the envelope; their goldens change shape only (classified).
- **D5: errors and statuses, one table.** `invalid_param` → exit 2 / `400`; `not_found` (repository, target, table, service, snapshot) → exit 3 / `404`; `ambiguous` (with `candidates`, design §9.1: never a silent pick) → exit 4 / `409`; `no_live_snapshot` → exit 3 / `404`; `snapshot_not_retained` → exit 3 / `410`; `cypher` (syntax, timeout: `kind` `cypher_timeout`, read-only violation) → exit 5 / `422`; `busy` and `deadline_exceeded` → (server only) `503`; anything else → exit 1 / `500`. The CLI's text mode keeps its current messages.
- **D6: limits.** Defaults and maxima are the design's (§11.2) and the existing constants (verified fact 7); a request outside a maximum is `invalid_param`, never silently clamped (the CLI's `ensure!` behaviour today, verified fact 9).

  | Limit | Default | Maximum | Applies to | Today |
  |---|---|---|---|---|
  | `depth` (callers) | 1 | 25 | Q1 | as is |
  | `depth` (path) | 12 | 25 | Q4 | as is |
  | `hops` | 4 | 8 | Q4, Q3 | as is |
  | `nodes` (reachability) | 200,000 | 200,000 | Q2, Q3 | as is (Q2 reports a bare `truncated: bool`, verified fact 7) |
  | `tree` (rendered tree nodes) | 5,000 | 5,000 | Q1 (new), Q4 | Q4 only; Q1 has no cap |
  | `work` (counted operations per request) | calibrated in phase 6 on the fixtures and re-calibrated on the benchmark (amendment) | same | every question | none |
  | `rows` (Cypher) | 10,000 | 10,000 | Cypher | none |
  | Cypher `statement_timeout` | 2 s | 30 s | Cypher | fixed 2 s |
  | wall-clock deadline (server) | 10 s | flag | every request | n/a |
  | concurrency (server) | 4 running, 16 queued | flags | every request | n/a |

  The work cap is deterministic: it is a count of examined elements, so the same request truncates at the same element on any machine. The wall-clock deadline is a safety net that never produces a body (D4/D5), because a time-cut answer would depend on machine speed (design §4.4's reason for having no parser timeout).
- **D7: local-only, no authentication in M5.** Loopback bind only (startup error otherwise); the Host allow-list against DNS rebinding; no CORS headers, and `POST` accepted only with `Content-Type: application/json`, which a cross-origin page cannot send without a preflight that gets no CORS approval. Authentication (a token file) and remote binding are M6 work if remote access is ever asked for. The user's environment runs local services only.
- **D8: concurrency model.** A semaphore of `--workers` (default 4) running requests and a bounded queue (default 16); a request that finds the queue full gets `503 busy` at once. A pool of `--workers` read-only connections (`default_transaction_read_only = on`, `search_path` as `Store::connect`), one per running request, hand-rolled (no pool crate).
- **D9: Cypher as `rb_reader`.** `rb cypher` and `POST …/cypher` run `SET LOCAL ROLE rb_reader` inside their read-only transaction, so a function call reachable from Cypher (for example `pg_read_file`, which the compose superuser may call) is denied. Phase 0 checks that AGE's `cypher()` works under that role with the grants of migration 0006.
- **D10: retention and the graph lifecycle (fork F3).**
  - The AGE graph exists only for the live snapshot (design §8.4: "the old graph is dropped when its snapshot is retired"). After the flip commits, the previous live snapshot's graph is dropped in its own transaction and its `age_graph` set to `NULL`. Today retired snapshots keep their graphs until deleted (verified fact 5).
  - Relational rows: the live snapshot plus the `N` newest retired ones (`--keep N`, env `RB_KEEP_RETIRED`, default 2 = `KEEP_RETIRED` today; design §8.3's "default 3" counted the live one and is annotated). `failed` rows are removed.
  - Every `create_graph`/`drop_graph` takes `pg_advisory_xact_lock(RB_AGE_DDL_LOCK)` first (design §14's mitigation), and each drop is its own transaction: dropping several graphs in one transaction takes a lock per label table of each graph (phase 0 records the error and `max_locks_per_transaction`).
  - The snapshot row is inserted inside the publish transaction; on failure, after the rollback, a `failed` row is inserted with the same `(repo, commit, tool_versions)`. A visible `building` row can then only be left by a pre-M5 binary; `rb gc` removes it.
- **D11: `rb diff` semantics.**
  - **Identity:** nodes by `(kind, key)`; edges by `(src kind, src key, kind, dst kind, dst key, provenance)`; both are the canonical dump's sort keys (verified fact 10). Surrogate ids never appear.
  - **Sections:** nodes added, removed, changed (`name` or `attrs` differ: before and after); edges added, removed, changed (`certainty` or `attrs` differ: before and after), and `evidence_only` (only the evidence differs: counted in text, listed in JSON); diagnostics as a count per kind before and after (`--diagnostics` lists the multiset difference of the dump's `D` lines).
  - **Order:** the canonical dump's order within each section.
  - **Summaries** (computed with the card's and Q3's functions on each graph): endpoints added/removed (by key, display with router), table access added/removed as `(service, table, op)`, service dependencies added/removed as `(from, to, via)`, and per edge kind the count of certainty raises and drops.
  - **Selectors:** a snapshot id, or a commit prefix unique among the repository's kept snapshots (ambiguous → `ambiguous` with candidates). Defaults: `from` = the live snapshot's `parent_id` if still kept, else `invalid_param` naming the kept ones; `to` = live. Two snapshots of different repositories may be compared (determinism checks do).
- **D12: tool versions.** `rb diff` never re-indexes. When `tool_versions` differ, the header lists the differing keys and JSON carries `tools_differ: [keys]`; design §14's "re-indexing both snapshots with the same tools" stays a user action (`rb index --rev <commit> --force`), annotated.
- **D13: facts cache.**
  - `--no-cache` bypasses reads and still writes the rows it extracted (M4a open item 4), like SCIP's existing write-only cache (verified fact 11); its help text says so.
  - `rb cache prune --facts` deletes rows whose `extractor` is not the current one; `--scip` deletes `rb.scip_index` rows whose `indexer_digest` is not a current image identity. It prints rows and bytes removed. Never implicit (an older binary sharing the database still needs its rows).
  - Compaction and compression: M6, or a documented gap if the benchmark's cache exceeds 25% of its database size (S24).
- **D14: benchmark protocol (S23–S26).**
  - **Hardware of record:** Apple M4, 10 cores, 16 GiB; Docker Desktop VM 10 CPUs, 7.75 GiB (`docker info`, 2026-10-07). Design §12.5's targets assume 16 cores; numbers are reported as measured, with no scaling claim.
  - **Latency:** the server warm (index built), ≥ 20 warm-up requests, then ≥ 200 samples per question kind from a sampling rule fixed before the run (M3b's rule over the candidate set: sorted by key, N = ⌊count/200⌋, indices ⌊N/2⌋ + i·N); p50, p95 and max from a script; server-side time from the `Server-Timing` header and client-side time from the client; host `uptime` load averages before and after; two runs.

- **D17: `?snapshot=` everywhere.** Every question takes `--snapshot <id>` / `?snapshot=<id>` (design §9); the snapshot must belong to the repository and be kept; otherwise `snapshot_not_retained` or `not_found`. Questions on a retired snapshot work from relational rows; `rb cypher` on a retired snapshot is `invalid_param` ("no AGE projection", D10).
- **D18: pagination.** Flat lists (`find`, `services`, `snapshots`, `diff` sections, Cypher rows beyond the cap are *not* paginated: they truncate) take `limit` and `offset` and return `total` and `next_offset` (`null` at the end). Snapshots are immutable, so offset pages over one snapshot never drift; every listed order is total (ties end on kind and key, bytewise). Trees (callers, path, impact, table-deps) are not paginated; they are capped (D6).
