## New findings

### K1: major. Java Unicode escapes other than `\u000a`/`\u000d` restructure a file for javac only. No agreement reason fires, and the exact `CALLS` gets Tree-sitter's (wrong) caller.

**Cause.** JLS §3.3 translates every `\uXXXX` before lexing:
- `*/` ends a block comment for javac;
- `"` ends a string literal for javac.

Tree-sitter-java treats both as text inside the comment or string. That is J2's class with other characters.

`comment_terminator` (`crates/rb-scip/src/decode.rs:279–291`) looks only for a lone CR and `\u000a`/`\u000d`.

`definition_disagreement` (`crates/rb-indexer/src/scip.rs:658–690`) only looks at global method and type **definition** occurrences. It flags one only when it sits on a Tree-sitter token or inside a Tree-sitter function or method. When the code javac sees is an initializer block or a field's lambda, there is no such definition. The edge source is Tree-sitter's enclosing definition (`scip.rs:360–368`, used at `:398` and `:425`) and is never checked against the index.

**Repro.** Real image, `rb-scip-java:0.13.1`, `--no-cache --force` today. Project `t8esc`: UTF-8 pom, ASCII sources, line 4 of each file:

| File | Line 4 | javac reads | Tree-sitter reads |
|---|---|---|---|
| `Esc1.java` | `int good() { /* note */ return a(); } { /* */ b(); }` | `good(){return a();}` + initializer `{b();}` | one comment, `b()` inside `good` |
| `Esc2.java` | `void good() { String s = ""; a(); } { String t = ""; b(); }` | `s = ""; a();` / initializer `t = ""; b();` | one string, `b()` inside `good` |
| `Esc3.java` | `int good() { /* \uuu002A/ return a(); } Runnable r = () -> { /* */ b(); };` | field `r`'s lambda calls `b()` | `b()` inside `good` |

- **Observed.** `rb status`: `documents rejected 2 (comment_terminator 2)` (CommentCr and UEsc only), `unmatched 0`. The dump has:
  - `Esc1#good() CALLS Esc1#b()` (`scip`, 5) `[3,55,3,56]`;
  - `Esc2#good() CALLS Esc2#b()` `[3,67,3,68]`;
  - `Esc3#good() CALLS Esc3#b()` `[3,71,3,72]`.
- **All three are false.** The index contradicts each one itself: the probe (real decoder) shows `Esc1#good().` with enclosing range `[3,4,3,46]`, `Esc2#good().` `[3,4,3,44]` and `Esc3#good().` `[3,4,3,43]`, and each `b` reference lies outside that range.
- **Also lost.** The true `good → a` (Tree-sitter sees `a()` inside a comment or string).
- **Same with the reasons off.** On the positive-control binary (reasons 1–4 disabled), `definition_disagreement` rejects CommentCr and UEsc and still passes Esc1–3.
- **Variant that is caught.** `}` as a closing brace (`tsprobe`) makes Tree-sitter swallow the next method. `a()`'s definition then lies inside `good`, so `definition_disagreement` fires (coverage only).

**Prevalence.** 0 such files in the seven public repositories. The construct is legal Java and rare outside obfuscated or generated code, but S5 and invariant 2 admit no exceptions, and amendment 64 claims this class is impossible.

**Expected.** No exact edge whose source the index contradicts. Either:
- check each reference against the innermost SCIP definition whose enclosing range contains it, and reject the document (or count the edge unmatched) when that is not the Tree-sitter enclosing definition's symbol (pass 7 suggested this for J2); or
- extend `comment_terminator` to any `\uXXXX` outside a string or char literal's own escape role. Simplest: any Unicode escape at all in a scip-java document, which costs coverage only.

**Regression test.** A join unit with the measured Esc1 occurrences (`good().` with enclosing `[3,4,3,46]`, `b().` reference at `[3,55]`) and Tree-sitter facts that put `b()` in `good`, expecting no `good → b`. Plus a decoder unit for `*/` and `"` if the rule route is taken.

### K2: major. The source-encoding signal is a literal-pom-element scan. Encodings set elsewhere give false exact `CALLS`, and `definition_disagreement` does not back it up when only references shift.

**Cause.** `rb_scip::maven_source_encoding` (`crates/rb-scip/src/jobs.rs:210–239`) reads only `<project.build.sourceEncoding>`, `<maven.compiler.encoding>` and `<encoding>` elements of the poms under the build root:
- It resolves `${p}` against the **first** `<p>` element in **any** pom, not along the module's parent chain (`:222`).
- Elements with attributes are skipped (`:257`).

javac's actual encoding can come from:
- `.mvn/maven.config` (`-Dproject.build.sourceEncoding=…`, which overrides the pom);
- `<compilerArgs><arg>-encoding</arg>…`;
- a module that overrides a property the encoding refers to;
- a parent pom outside the repository (the existing open item).

The contract calls `definition_disagreement` "the backstop there", but it looks at definitions only. When the non-ASCII text precedes only references on its line, nothing fires.

**Repro.** Real image, `--no-cache --force` today. Each project has `Plain.java` and a `<Name>.java` whose line 6 is:

`    int p(A a) { /* ` + 17 × `é` + ` */ return a.z(); } { new B().z(); }`

with `static class A { int z() }` and `static class B { int z() }` above it. The file is valid UTF-8.

| Project | Where ISO-8859-1 comes from | Observed exact edge (false) |
|---|---|---|
| `t8cfg` | pom says `UTF-8`, `.mvn/maven.config` says `-Dproject.build.sourceEncoding=ISO-8859-1` | `Cfg# CALLS Cfg#A#z()` `[5,84,5,85]` |
| `t9arg` | pom declares no encoding; `maven-compiler-plugin` `<compilerArgs><arg>-encoding</arg><arg>ISO-8859-1</arg></compilerArgs>` | `Arg# CALLS Arg#A#z()` `[5,84,5,85]` |
| `t8mod` | root: `<enc>UTF-8</enc>`, `<project.build.sourceEncoding>${enc}</…>`; module `z` overrides `<enc>ISO-8859-1</enc>` | `Mod# CALLS Mod#A#z()` `[5,84,5,85]` |

- **Status line.** Each `rb status` reads `documents rejected 0 … unmatched 2`.
- **The edge is false.** Byte 84 is the `z` of `new B().z()` in the instance initializer, which calls `B#z()`. The probe shows javac's `A#z()` reference (true byte 67, inside `p`) converted to `[5,84]`, and the local `a` converted onto `)` at `[5,82]`.
- **Lost.** `p → A#z()` and the initializer's `→ B#z()`.
- **Reasons off.** On the positive-control binary (reasons 1–4 disabled), the same layout in `t8enc/Enc.java` (an ISO-8859-1 pom) is **not** rejected either, and gives `Enc# CALLS Enc#A#z()` `[5,84]`. So `definition_disagreement` is no backstop for J1's class. It catches pass 7's `Enc` only because there a definition (`p`) shifted onto another name.

**Prevalence.**
- 0 in the seven public repositories, whose builds declare UTF-8 in the pom.
- `<compilerArgs>-encoding` and `maven.config` properties are legal and occur in older builds.
- A false edge needs a non-ASCII run before a same-named call in another member on the same line. Far more often the shift just loses edges (the `unmatched` count).

**Expected.** Do not convert a document when javac's encoding is unknown. Options:
- (a) Read the effective encoding from the build in the fetch phase: `help:evaluate -Dexpression=project.build.sourceEncoding` per module, plus the compiler plugin's effective `encoding`/`compilerArgs`, then treat anything not UTF-8, or unknown, as `source_encoding`.
- (b) Make the agreement check see reference shifts: reject a document when any occurrence fails the name guard. Here `unmatched 2` is exactly the two shifted occurrences: `local 0` at `)` and `B#z()` at an empty span.

Option (b) also narrows K1 where shifts are involved.

**Regression tests.**
- A `maven_source_encoding` (or fetch-phase) unit for `.mvn/maven.config`, `compilerArgs` and a module property override.
- A join unit with the measured `Cfg` occurrences (`A#z()` at `[5,84]`, `local 0` at `[5,82]`) expecting rejection or no `Cfg# → A#z()`.
