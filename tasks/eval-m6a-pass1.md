## Findings

### Z1 (minor): `take_while(is_under)` misses workspace members shadowed by a sibling — D5's membership rule violated in the safe direction

- **Repro (unit-level, deterministic, no containers):** in `rb_scip::jobs` (use the `workspace_summary` helper), files `mods/package.json` (`{"workspaces": ["app"]}`), `mods/package-lock.json`, `mods/app/package.json`, `mods/app/tsconfig.json`, `mods-old/package.json`, `mods-old/tsconfig.json`. Sorted roots: `mods < mods-old < mods/app` (`-` 0x2D `<` `/` 0x2F). The member loop (`jobs.rs:292-295`) does `package_roots[k+1..].iter().take_while(|c| is_under(c, root))`: for root `mods`, the first candidate `mods-old` is not under it, so the scan stops and `mods/app` is never examined.
- **Observed:** jobs `mods-old` (own, unpinned) + `mods/app` (own, unpinned); `mods` groups nothing (`members` empty, no `workspace_members`). **Expected (D5):** `mods` groups `mods/app` (`{app}`), `mods-old` its own job.
- **Why minor, not blocking:** the missed member falls back to today's unpinned job — the contract's safe direction; no false edge, no invented grouping, no key escape (each job's key covers its own export; `owner_root` is independent of grouping, so no double-index). It matches no closing-bar 3(a–e) clause (the converse of 3(c)'s false-admission case). It does contradict D5's letter ("a member is a package root strictly under a workspace root whose path matches"), so it should be fixed test-first before close, not shelved as residue.
- **Where:** `crates/rb-scip/src/jobs.rs:290-305` (comment at :290 asserts contiguity that holds only for string-prefix order, not for segment-aware `is_under`). Any sibling whose post-root char is `< '/'` (`-`, `.`, `+`, …) between a workspace root and its members triggers it (e.g. `packages-old` vs `packages/app`).
- **Fix direction (test-first amendment):** add the repro above as the failing test (`members` must be `{app}`); break the scan on the string-prefix boundary instead of `is_under` (candidates sharing the string prefix `root + "/"`… precisely: continue while the candidate starts with `root` as a string, which is contiguous in sorted order and misses nothing), keeping `is_under`+trie as the per-candidate matcher so the S19 linearity bound still holds (a bare `filter` is O(n²) and would fail `workspace_membership_grows_linearly`; my survived mutant M3 demonstrates both the gap and the constraint).
- **Regression test:** the repro, plus a growth-shape with shadowing siblings to pin linearity.

### Z2 (minor note): a lockfile link resolving to the repository root (`""`) exports the whole repository — safe, no rule violated

- **Repro:** `link_targets("a/b", {"packages": {"node_modules/x": {"resolved": "../..", "link": true}}})` → `Ok([""])` (probed live, reverted). `job_files` then exports every tracked file (`under("")`); the key covers exactly the export (amendment 6a), documents outside the root are ignored and counted, no path leaves the repository, deterministic.
- **Why a note:** reachable only via a lockfile npm never writes (`resolved` is always a real package dir in practice); D7's letter ("a target inside the repository … adds its tracked files") covers it; worst case is wasted work and odd counters, never a false edge. The Z1 amendment may decide `""`→`unsupported` or keep-and-count; either is fine.
